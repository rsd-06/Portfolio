When building a developer portfolio, the instinct is often to reach for a heavy, database-backed architecture. We wire up PostgreSQL, configure ORMs like Prisma, and spin up CMS dashboards just to serve a few blog posts and project showcases. 

But for personal sites, this is usually overkill. In this post, we explore why a **Git-backed Markdown architecture** is the cleanest, most performant way to build a modern developer portfolio.

## The Problem with Databases for Portfolios

Traditional database-backed portfolios introduce unnecessary friction:
- **Maintenance overhead**: You have to manage database migrations, hosting, and uptime.
- **Authoring friction**: Writing content means logging into a CMS dashboard instead of using your favorite IDE.
- **Latency**: Every page load requires a database query (unless heavily cached).

## The Markdown & Git Approach

Instead of a database, treat your Git repository as the single source of truth. By writing your content in **MDX (Markdown + JSX)**, you combine the simplicity of Markdown with the power of React components.

### The Architecture

1. **Content Layer**: MDX files stored directly in your `src/content/` directory.
2. **Parsing Layer**: A build-time script (e.g., using `gray-matter` and `next-mdx-remote`) that parses the files and extracts metadata.
3. **Rendering Layer**: Next.js statically generates the pages at build time.

### Show Me The Code

Here is the core logic for reading MDX files from the filesystem. Notice how simple it is compared to a database query:

```typescript
import fs from 'fs';
import path from 'path';
import matter from 'gray-matter';

const CONTENT_DIR = path.join(process.cwd(), 'src/content/blogs');

export function getBlogPosts() {
  const files = fs.readdirSync(CONTENT_DIR);
  
  return files.map((filename) => {
    const rawContent = fs.readFileSync(path.join(CONTENT_DIR, filename), 'utf-8');
    const { data, content } = matter(rawContent);
    
    return {
      slug: filename.replace('.mdx', ''),
      title: data.title,
      date: data.date,
      content
    };
  });
}
```

### Why This Wins

1. **Zero Database Cost**: You don't pay for a database. Your hosting (like Vercel or Netlify) handles the static files for free.
2. **Git Versioning**: Your blog posts have commit history. You can branch, review, and rollback content just like code.
3. **Instant Loading**: Because the content is read at build time, Next.js can generate static HTML. The Time to First Byte (TTFB) is virtually zero.
4. **Developer Ergonomics**: You write in your IDE, push to GitHub, and your CI/CD pipeline deploys the site. 

## When to use a Database

If your site requires user authentication, dynamic comments, or highly personalized feeds, a database is unavoidable. Tools like **Convex**, **Supabase**, or **Firebase** are excellent for these use cases. But for read-heavy, author-centric portfolios, stick to Markdown.
